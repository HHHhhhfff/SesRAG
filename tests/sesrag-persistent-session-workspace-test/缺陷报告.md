## 2. WS-DEF-001：归档会话呈现未完全符合PRD

- **问题是什么**：PRD FR-TH-01要求归档Thread从归档列表打开、取消归档后回普通列表。当前界面把归档和普通Thread放在同一列表，只显示“已归档”，没有独立归档入口或筛选。归档并未删除历史，归档后的写操作受拒绝，取消归档可恢复继续对话；缺口是列表组织/选择语义，不能解释成数据库丢失或取消归档失败。
- **来源与状态**：UI_001预期明确要求记录混排差异，R1/R2均实测通过并同时观察到该差异；这是PRD对照发现，不篡改为UI_001自动断言失败。调研§4.1/LIMIT-01也已提示。
- **代码定位**：`frontend/src/stores/thread.ts::loadThreads/loadMoreThreads`固定`include_archived:true`；`loadThreads`先恢复有效已存选择，否则选未归档项，因此有效归档偏好仍可恢复为只读。`setArchived`更新原列表和详情，没有迁移到独立列表。`frontend/src/components/ThreadList.vue`对同一`threads`循环渲染并加归档标记，没有归档过滤控件；`frontend/src/pages/WorkspacePage.vue`负责归档操作/只读呈现。后端`backend/application/session_threads.py::list_session_threads/patch_session_thread`已支持归档过滤及状态修改。
- **原因**：前端选择了统一混排呈现，没有完整实现PRD文字中的普通/归档列表区分。不是缺Docker、Playwright或PG条件，也不能以API正确推导UI完全符合。
- **影响与程度**：影响FR-TH-01的用户组织和定位体验；归档仍出现在普通列表，有效偏好可恢复归档只读会话。当前未见事实丢失、权限绕过或错误可写；不阻断主聊天链路，但不能宣称该需求完全验收无差异。
- **真实证据**：[R1 UI_001](artifacts/ws-20261023t020902z-9fa22610/categories/workspace/UI_001.json)、[R2 UI_001](artifacts/ws-20261023t030707z-c936fff7/categories/workspace/UI_001.json)及各自同目录result；两轮原文观察均为“界面为混排标识，未提供独立归档筛选页”。
- **复现参考**：从仓库根运行`pwsh -NoProfile -File tests/sesrag-persistent-session-workspace-test/run-workspace-tests.ps1 -Mode Selected -Categories 'workspace'`，入口结束后查看新run_id的UI_001证据。该测试会部署并销毁临时页面；如人工观察，应在测试运行期间按其动态地址访问，不能使用已经销毁的旧端口。操作为创建带历史Thread→归档→观察同一列表仍有归档项→打开只读→取消归档。
- **处理方向**：在现有Thread列表/store中提供普通/归档视图及相应分页/选择规则；保留服务端归档只读和事实身份。需同步UI_001/SES归档断言、前端组件测试、接口说明中用户行为部分；不通过删除现有历史或只隐藏标记“修复”。产品若决定接受混排，应先显式调整PRD/ADR验收口径，当前没有该变更授权记录。
- **修复状态**：本任务只测试与报告，未修改产品；待后续修复或明确产品决策。

## 3. WS-DEF-002：OpenAPI应用版本落后于项目版本

- **问题是什么**：真实`GET /openapi.json`返回`info.title=SesRAG`、`info.version=0.1.0`，而`pyproject.toml`和`frontend/package.json`版本均为0.2.0。项目版本、HTTP路径v1/v2、Run/Event schema版本是不同概念；该元数据错误不表示v2路由未接线，也不能证明schema2不工作。
- **问题定位与原因**：`backend/app.py::create_app`创建`FastAPI(title="SesRAG", version="0.1.0", ...)`时硬编码旧值；包版本更新后没有同步应用元数据。
- **影响**：OpenAPI页面和读取info.version的部署识别、诊断或客户端工具显示错误版本；目前未见聊天、迁移、SSE行为受影响，建议P2处理。
- **证据**：[R1补充现场记录](artifacts/ws-20261023t020902z-9fa22610/diagnostics/openapi-metadata.json)，UTC `2026-10-23T02:15:54.6306162Z`；这是一项额外只读请求，未新增注册case，不能更改104例计数。
- **复现参考**：在终端A启动独立环境：`pwsh -NoProfile -File tests/sesrag-persistent-session-workspace-test/run-workspace-tests.ps1 -Mode Environment -HoldSeconds 120`。等待日志出现“观察窗口开始”后，在仓库根的终端B执行以下只读命令，仅读出公开地址和版本，不输出私有session全文。窗口结束由入口自动销毁；旧R1地址已失效。该复现需等其他正式轮次结束，不并行争用活跃锁。

  ```powershell
  $suitePath = 'tests/sesrag-persistent-session-workspace-test'
  $activeRunDir = Get-ChildItem -LiteralPath "$suitePath/runtime" -Directory | Sort-Object Name -Descending | Select-Object -First 1
  $apiBase = (Get-Content -LiteralPath (Join-Path $activeRunDir.FullName 'session.json') -Raw | ConvertFrom-Json).endpoints.api_base_url
  (Invoke-RestMethod "$apiBase/openapi.json").info | Select-Object title, version
  ```
- **处理方向**：以单一版本源构造应用版本或同步该声明，并增加轻量版本一致性验证。保留API兼容策略和schema版本的独立语义，不把所有v1路径改v2来修元数据。
- **原因类型 / 状态**：类型1，应用元数据实现问题；补充发现，尚未修复。

## 5. WS-DEF-004：秘密扫描日志的统计名称不准确

- **问题是什么**：QLT_006实际观察中R1写“507份当轮公开证据”、R2写“504份当轮公开证据”；这些数字来源于helper的`files_scanned`，它统计本轮artifact文件、Git跟踪文件和frontend/dist文件的合计扫描次数。该数字并不是公开artifact份数，也不承诺去重。镜像25288成员、311个Git文件等另外有记录，若不解释，读者会误以为扫描范围被重复或夸大。
- **代码定位与原因**：`tests/sesrag-persistent-session-workspace-test/tooling/orchestrator.mjs::resourceHelper`的`audit-artifact-secrets`分支依次`walk(artifacts)`、遍历`git ls-files`、`walk(frontend/dist)`，共用`scanned`计数；`specific_test_script/quality-tests.mjs`的QLT_006将`reportAudit.result.files_scanned`插值为“份当轮公开证据”。原因是日志标签与helper统计边界不一致，属于类型3测试工程报告表述问题。
- **影响与程度**：影响扫描数量说明的精确性，不改变`files_with_secret=0`、镜像matches为空和秘密断言；本次未因此出现failed、blocked或工程错误，不能把它说成产品泄密。建议P2维护。
- **真实证据**：[R1 QLT_006](artifacts/ws-20261023t020902z-9fa22610/categories/quality/QLT_006.json)中的`artifact_audit.files_scanned=507`、[R2 QLT_006](artifacts/ws-20261023t030707z-c936fff7/categories/quality/QLT_006.json)中的504，两轮`files_with_secret=0`；各自同目录`secret-image-scan.json`均记录25288成员及零匹配。最终R1/R2证据索引分别216/213项，是另一个时点/范围，也不能拿来替代helper当时计数。
- **复现参考**：按总入口运行`-Mode Selected -Categories 'quality'`，结束后查看QLT_006；计数随证据/跟踪文件数量变化，不应断言永远507。只核对helper范围与日志命名，不手工改写原始日志。
- **处理方向 / 本次处理**：本报告和测试报告纠正口径，用例回填已说明它是合计扫描次数；后续将脚本措辞改为“合计扫描次数”或分别返回各扫描面计数，并补相应报告协议验证。为保持两轮完全同源，本轮未修改脚本，原始证据保持原样。
- **状态**：报告已解释；测试脚本措辞待后续修订。
